決定日: 2026-11-03（JST）。決定者・運用責任者: sskohei。根拠: [Issue #4](https://github.com/sskohei/Alter/issues/4)の目的と、本人による対象者・責任者・期限の回答。ADR-009〜012に対応する。2026-11-08にsskoheiの承認で保存・運営操作をDB＋専用CLIへ変更した（ADR-014）。これは実装に渡す契約であり、招待判定や削除ジョブが実装済みであることは意味しない。

## 招待対象と手順

対象はsskoheiが直接招待する18歳以上の知人、最大10人。一般募集・自己申込・招待の譲渡は行わない。年齢は本人申告で確認し、生年月日や本人確認書類を収集しない。招待・削除等の窓口は招待時に使用したsskoheiとの私的な連絡経路とし、公開Issueに個人情報を書かせない。招待案内には以下の利用説明と窓口を添える。

MVPの許可リストはSupabase PostgreSQLの`invitations`・`invitation_identities`を正本とし、APIと運営専用CLIだけが扱う。ブラウザの`anon`/`authenticated`による直接参照・更新を禁止する。招待者の実データはGit・環境変数・公開ログに含めない。1人の招待に内部招待ID、許可する`(provider, provider_user_id)`の組、紐付けるSupabase `sub`、有効/失効状態を管理する。providerは`google`/`github`だけ。メールアドレス・表示名・GitHubハンドル・クライアント申告のIDでは許可しない。Google/GitHub両方を使う場合は両方のIDを登録するが、人数は1人と数える。運営が10人枠と本人を確認してから有効化し、操作の時刻・担当・結果だけを監査する。

1. sskoheiが私的な経路で対象者と利用するプロバイダーを確認する。未登録者はOAuthに成功してもアプリを利用できない。
2. 必要な場合は初回OAuth後のSupabase Auth管理情報からプロバイダーIDと`sub`を取得し、招待した本人と別経路で照合して登録する。この時点までは業務プロフィールを作らない。Authに一時ユーザーができることとアプリへの入場許可は区別する。招待を有効化しないAuthユーザーは30日以内に運営が削除し、プロフィールを作らない。
3. APIはJWT検証と既存の停止/削除状態の確認後、Auth側から取得した信頼できるidentityと許可リストのprovider ID・`sub`の一致を検証する。ユーザー編集可能なmetadataやメール一致を根拠にしない。紐付け済みの別プロバイダーが招待外を迂回しないよう、Auth側の連携済みGoogle/GitHub identitiesはすべて当人の招待に登録されていることを要求する。未登録identityの追加後は運営照合まで拒否する。少なくとも1つの許可identityが必要で、未対応provider・判定不能も拒否する。
4. 許可後だけ`GET /users/me`でプロフィールを作成する。再読込・同時要求でも同じ`sub`に1プロフィールのみ。別プロバイダーを追加するときも運営による本人照合と同じ`sub`への紐付け確認が必要。メール一致での自動統合や、別`sub`への自動移管は行わない。
5. 削除要求時はDBで削除状態・AI停止・未配信取消・招待失効・監査を同一トランザクションで確定してからAuthユーザーを削除する。古いJWTにもDB状態を適用する。トランザクションが失敗した場合はAuth削除へ進まず再試行する。削除後の再OAuth・新しい`sub`で自動復帰させない。再参加は新たな本人照合・招待・初期OFFの同意から行う。

一般業務APIは毎回、JWT→既存プロフィール/削除要求の停止・削除状態→招待→所有権の順で確認する。停止/削除状態があれば招待失効の判定より優先する。Auth/プロフィールが消去済みの場合は招待失効により拒否する。未認証/無効JWTは`401 UNAUTHENTICATED`、有効JWTでも招待外は`403 INVITATION_REQUIRED`、停止・削除要求済みは`403 ACCOUNT_INACTIVE`。招待DB照会障害・招待データ不整合・Auth照会障害は`503 AUTHORIZATION_UNAVAILABLE`として業務処理を行わない。拒否時はプロフィール、AI、ジョブ、LLM呼出を作らず、許可リストや他人の登録状況を応答しない。削除状態はプロフィールの新規作成より先に確認する。`/health`は対象外。

削除要求者向けの状況確認だけは、本人JWT/再認証で本人の削除要求ID・状態・期限を返せるようにし、業務データを返さない。Auth削除後は招待時の私的窓口で本人を確認して結果を伝える。他の利用者の存在を明かさない。Bot/Worker/CronもDBの停止・削除状態を予約・実行・配信直前に確認する。運営による招待失効もAI停止・未配信取消・監査と同一DBトランザクションで確定する。基礎DDL #6 は完了済みで、招待用の追加migration・CLI・共通認可は #7、画面は #9、削除は #30/#31 に引き渡す。

## 運営専用CLIとDB更新

運営責任者sskoheiが、本人確認後にCLIで登録・一覧確認・プロバイダー追加・失効を行う。MVPに招待管理Web画面や公開の招待管理APIは設けない。コマンドは`alter-invitations`（`backend/alter_domain`の`alter_domain.cli.invitations`）で、#7 で確定した。未配信取消は対象テーブル追加時の #13/#26/#28、削除要求との連動は #30 で同じ共通ドメイン処理へ接続する。

- CLIはAPIと共通のドメイン処理・リポジトリを呼び出し、対象環境を明示してサーバー側DBへ接続する。運営用資格情報をWebへ渡さず、実識別子をシェル履歴・共有ログへ残さない入力方法を用意する。一覧の既定表示は内部招待ID・状態とし、識別子の詳細表示は運営の明示操作に限定する。
- 登録時はAuth管理情報から取得したidentityと`sub`を本人照合し、招待・identity・監査を同一トランザクションで保存する。10人枠は有効な招待を人数として数え、登録/再参加処理間で共通ロックを取り、同時登録でも10人を超えない。同一`sub`や同一provider IDの重複はDB制約で拒否する。
- identity追加も本人照合と同一`sub`の確認を必須とする。失効済み招待を通常の登録・追加処理で自動有効化しない。再参加は新たな本人照合・招待と初期OFFの同意から開始する。
- APIは一般業務リクエストごとにDBの有効な招待とAuth側identityを照合する。環境変数への一覧の複製や、リクエストをまたぐ許可結果のキャッシュは行わない。失効コミット後の要求を拒否し、実行中のジョブも予約・実行・配信直前にDB状態を再確認する。
- 監査は`audit_events`に内部招待ID・操作種別・運営担当・時刻・結果を記録し、provider ID・`sub`・トークンを監査metadataへ複製しない。更新失敗時はロールバックし、識別子を含まない失敗コードと担当・時刻を別途記録する。
- 失効後は即時に利用不可とする。失効の再実行は冪等とし、最初の失効日時とパージ期限を延長しない。招待とidentityの識別情報は失効時から30日以内、アカウント削除時は削除要求時から30日以内の早い期限でパージする。招待が存在しない状態でも拒否するため、Auth削除後も自動復帰しない。バックアップ復元時の失効・削除再適用を公開前に検証する。

### CLIの使い方（#7）

リポジトリrootで実行する。接続先は`.env`/環境変数の`DATABASE_URL`・`SUPABASE_URL`・`SUPABASE_SECRET_KEY`。

```bash
uv run alter-invitations --env local --operator sskohei list                    # 内部招待ID・状態・プロバイダー種別のみ
uv run alter-invitations --env local --operator sskohei list --show-identifiers # 照合作業中だけ。subとprovider IDも表示
uv run alter-invitations --env local --operator sskohei register                # subを対話入力→Authの連携ログインを表示→registerと入力
uv run alter-invitations --env local --operator sskohei add-identity <招待ID>    # 同じsubに新しく連携したGoogle/GitHubを追加→addと入力
uv run alter-invitations --env local --operator sskohei revoke <招待ID>          # 失効・AI停止・監査を同時確定→revokeと入力（--yesで省略）
```

- `--env local|production`は必須。`local`はDB/Supabaseの接続先がローカル（127.0.0.1/localhost）でなければ中止し、`production`はローカルなら中止したうえで`production`の入力を求める。
- Supabaseの`sub`はコマンド引数ではなく対話入力で受け取り、シェル履歴に残さない。CLIはログファイルを書かない。
- `register`はAuth管理APIから取得したGoogle/GitHub identityをすべて登録する。Google/GitHub以外のログイン方法が連携されている、同じプロバイダーの複数アカウントがある、Authにユーザーがいない場合は登録しない。1つの招待に同じプロバイダーは1つまで（`UNIQUE(invitation_id, provider)`）。登録済みプロバイダーの別アカウントへの差し替えは失効と再招待で行う。
- 失敗した操作も、ロールバック後に`result=failure`と識別子を含まない`code`を監査へ記録する。招待の取得・状態確認・Auth照会など更新前の事前確認の失敗も含む（`invitation_not_found`・`invitation_revoked`・`auth_user_not_found`・`auth_unavailable`など）。確認入力の取り消しは失敗ではないので記録しない。監査の`metadata`は`operator`・`result`・`code`だけ。
- 失効済み招待と同じ`sub`/provider IDの再登録は、パージ（#30）まで一意制約で拒否される。

Discordは全体ONに加えて`/agent publish on`で対象ギルド・チャンネルと上記注意をephemeralで提示し、本人の確認後にギルド別同意を記録する。相手の同意と管理者設定も揃い、投稿直前に再確認できた場合だけ配信する。投稿先変更時は旧同意を無効化し、再確認まで未配信を止める。撤回後の再開で過去の未配信を自動復活させない。

同意/承認は本人ID、対象、文面版、人格版またはギルド/チャンネルID、時刻、ON/OFF、結果を監査する。本文・トークンは監査に含めない。重要な文面・公開先変更は再同意するまで対象処理を止める。API/Bot側でも同意を検証し、UI表示だけで安全性を保証しない。

## 収集・保持・削除

収集はAuth識別子、表示名、本人が入力した人格/興味、会話と出典付き記憶、同意・連携・費用・監査に必要な情報に限定する。住所・連絡先・公的ID・金融情報・健康等の機微情報、第三者の秘密は入力しないよう案内する。OAuthで得た不要な項目をアプリへ複製せず、Discord履歴を収集しない。非公開欄は任意・空が既定で、本人が必要と判断した一般的な補足だけ。LLM・他者・Discordに送らず、通常APIやログにも出さない。

保持期間の暫定運用値は[安全性の保持表](15-security-privacy.md)を正本とする。会話90日、記憶は180日で再評価し、不要分を削除する。再評価・延長理由を記録できなければ削除し、無期限に自動延長しない。期限は作成時刻起算とし、会話の起算は会話作成時刻、連携の30日は解除時刻、削除追跡の30日は完了時刻からとする。期限到達時点で参照・検索対象外とし、日次パージで除去する。記憶は出典会話が消えた時点でも削除するため、180日の上限より先に消える場合がある。

アカウント削除は要求時点で双方から関連会話と派生記憶/通知を参照不可にし、30日以内にDB・Storage・Authをパージする。使用量を保持する場合は本人/相手への再識別ができる紐付けを除き、本文を残さない。監査のactorだけでなくresource ID/metadataの識別子も匿名化する。Discord削除用の配送IDは会話CASCADE前に削除ジョブへ引き渡し、結果（成功/権限不足/対象なし/要再試行）を追跡する。ジョブにも本文を複製せず、完了後30日で削除する。sskoheiは失敗を確認し、30日を超える前に利用者へ残存理由と対応を連絡する。

バックアップは通常の参照経路に戻さず、復元時は削除要求・招待失効・期限処理を再適用してからサービスを再開する。バックアップと外部LLM側の保持・削除可能範囲は未検証であり、公開ゲートで実測/契約確認し、最長残存期間を利用者向け説明に明記する。アプリの30日以内パージを、外部コピーまで含む完全消去の保証として説明しない。

## 鍵管理と対応責任

sskoheiが鍵管理と削除対応の責任者。Bは実装・実行記録を、F/Dは本人操作と説明表示を確認する。非公開欄はAES-GCMで暗号化し、鍵はAPIのSecret管理だけに置く。既存の鍵版/nonceを使用し、平文・鍵をGit/ログ/Issueへ出さない。

人格暗号鍵は90日ごと、および漏えい疑い・管理権限変更時にローテーションする。新鍵作成→新規書込の版切替→旧版データのバッチ再暗号化→件数/復号検証→旧鍵廃止の順で行い、通常は開始から7日以内に完了する。旧鍵削除前にバックアップ復元も検証し、残存する旧暗号文の扱いを記録する。未完了・漏えい時は非公開欄への読書きを止め、責任者が影響範囲を確認する。OAuth/Bot/LLM/DB資格情報は別管理し、漏えい疑い時は即時失効・再発行、90日ごとに権限と交換可否を点検する。
