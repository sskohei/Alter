# 設計判断記録（ADR）

| ID | 決定 | 理由 / 再検討条件 |
|---|---|---|
| ADR-001 | WebとAPIを分離し、業務操作はFastAPIへ | 画面とビジネスロジックの責務を明確にする。APIはJWT/所有権を検証 |
| ADR-002 | Supabase Authを唯一のログイン基盤とする | Google/GitHubを統一。Discord OAuthは本人連携のみ |
| ADR-003 | Supabase CLI SQL migrationをDDL正本にする | RLS/索引/トリガーを一元管理。Alembicは使わない |
| ADR-004 | SQLAlchemy+Postgresジョブを採用 | 10〜100人で構成を単純化。待機時間/件数が閾値を超えたらRedis/Celeryを評価 |
| ADR-005 | API、Bot、Worker、CronをRenderで分離 | 常時接続とジョブをHTTP稼働から独立。無料Webのアイドル停止に依存しない |
| ADR-006 | MVPのWeb会話は参加者のみ、Discordはギルド別双方同意 | 公開事故を防ぎ、第三者公開は別設計とする |
| ADR-007 | 初期更新はPolling | 少人数では実装/運用負担が低い。遅延要件が厳しくなればSSEを評価 |
| ADR-008 | LLM供給元をadapterで未確定とする | 単価・安全性・日本語品質を試作で比較し、費用表に反映 |
